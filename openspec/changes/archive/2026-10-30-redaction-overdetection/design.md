# Design

## Measurement only

This change records a baseline and nothing else. It does not reduce redaction.
Every change that does (allow entries, a threshold) promises something about what
is redacted before indexing, and is written as its own change once Mark has
decided on the numbers recorded here.

`meting-overdetectie-05` already says how to measure a list: detection runs once
per document and the outcomes differ only in what sits behind it. An effect
across a reprocess is read from `suppressed_by_list` in the run's own records,
because a before/after across runs compares two code versions. The baseline here
follows both rules and is written to a new file next to the existing ones.

## Corpus, live run and output

- **Synthetic or fixture sentences only.** The pilot corpus is not used.
  Reading real documents is a data-handling decision for Mark, not for a
  builder.
- **Build and live run are separate.** The build delivers the harness, the
  counts-only guard test and the output format. The live run against
  OpenAnonymiser (`WORDSWORTH_OPENANONYMISER_URL`) is a separate step for Mark
  or the coding session.
- **Unreachable means "not run".** If OpenAnonymiser cannot be reached the
  report says "not run". A deterministic-only table is never shown as the
  baseline: it would look like a baseline and measure something else (no silent
  fallbacks).
- **The label.** The output file says "what detection would do now on this
  text", not "what it did". It re-runs detection over given text; it does not
  read what a past run produced (meting 05).

## What the corpus can and cannot show

LOCATION, ORGANIZATION, DATE_TIME and PHONE_NUMBER have no gold spans in the
corpus (meting 05), so every finding there counts as a false positive. The
absolute precision says little; only the difference between two runs on the same
detections does. Recall and leaks on seeded PII are the numbers a later change
must not move.

## Counts, never values

The five words are recorded as counts per type. A document passage or a detected
value does not appear in the file, the logs or the test output. A measurement
that logs a value turns the diagnostic into a leak of the thing it audits.

## Notes for the follow-up changes

- **DATE_TIME allow rules are invisible to the quasi-identifier check**
  (`combinations.py`). The check reasons over which types a profile pseudonymises
  and over declared combinations; an allow rule that lets a date through changes
  neither, so nothing there reports that a date, which can be part of a
  combination, is now in the clear. A DATE_TIME allow rule therefore needs its
  own review, not the combinations finding.
- **An allow entry for a type the detector never assigns is dead weight.** Allow
  rules never cross types, so an entry only works under a type the detector
  actually gives that word. The typed counts recorded here are what decides under
  which type an entry can do anything.

## Rejected alternatives

- **Ship allow entries or a threshold in this change.** The architect rejected a
  change whose requirements wait on a measurement; the measurement comes first
  and the fix is its own change.
- **Pick the mechanism now.** The two have different risks; the numbers decide.
- **Frequency as the criterion.** Meting 04: a frequent value can be a real place
  name (`naarden`). Candidates are generated by counts, decided by a human.
- **Use the pilot corpus for the baseline.** Needs Mark's decision on reading
  real documents; not for a builder.
- **Fall back to deterministic-only when the service is down.** Mislabels a
  different measurement as the baseline.
- **Run the live measurement inside the build.** Does not fit a build.
- **Mine the corpus for more words by reading it.** That is the human gate.
